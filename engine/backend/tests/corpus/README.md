# 回归语料库维护手册

这里的每个 `case-NNN-*/` 目录 = 一份曾经识别出错的真实文档（已脱敏）+ 人工确认过的正确提取结果。
它是 docx 导入识别质量的**唯一护栏**：任何识别规则的修改，都必须让全部 case 保持绿色。

## 目录结构

```
case-001-某某文档/
  input.docx              # 脱敏后的原始问题文档（勿手工重命名 case 目录编号）
  expected.md             # 人工确认过的正确提取结果（测试逐行比对）
  expected_warnings.txt   # 期望的提取警告（每行一条，可为空文件）
  note.md                 # 这份文档暴露了什么问题 + 脱敏了哪些字段
```

## 日常流程（三步，人或 AI 都照此执行）

1. **收录**：遇到识别不对的文档，在项目根目录执行

   ```
   .venv\Scripts\python -m backend.tests.corpus_tool add <问题文档.docx> --note "哪里识别错了"
   ```

   工具会自动脱敏（姓名/学号/导师姓名/文档作者属性，同长度替换保留格式特征）、
   生成 `expected.md` 草稿。然后**人工**做两件事：
   - 打开 `expected.md`，把识别错的地方改成正确答案（这是唯一必须人做的判断）；
   - 检查工具输出的脱敏替换表；若提示「未能自动脱敏」或「仍残留」，
     在 Word 里手工替换隐私信息后重新收录。

2. **修复**：修改 `backend/thesis_builder/docx_import/` 的识别规则，直到

   ```
   .venv\Scripts\python -m pytest backend/tests -q
   ```

   **新 case 变绿，且所有老 case 仍然绿**。这一条就是「扩大识别范围不伤准确性」的机械保证。

3. **守门**：任何涉及 `docx_import/`、`parser.py` 的改动，提交前必须跑一遍上面的 pytest。

## 期望结果有意变更时

识别行为的**有意**改进（比如新规则让某 case 的提取结果更好了）会让老 case 变红。
此时用 refresh 重新生成并人工确认 diff 是改进而非退化：

```
.venv\Scripts\python -m backend.tests.corpus_tool refresh case-001-xxx   # 缺省=全部
```

确认 diff 无误后连同代码一起提交。**禁止**为了让测试变绿而不看 diff 直接 refresh 全部。

## 脱敏约定

- 自动脱敏范围：学生姓名、学号、导师姓名（跨 run 拆分也能替换）、docProps 作者属性。
  替换为同长度假值（如 `刘春荣→张某某`、`202310010237→202300000000`），
  保证长度类识别特征（题目字数、学号位数等）不失真。
- 题目、学院、专业、班级默认**不**脱敏（识别语义依赖它们）；如某份文档的题目
  本身能定位到个人且作者在意，收录前先在 Word 里改题目再 add。
- 收录进 git 前，最后人工过一眼 `input.docx`（Word 打开搜一下真实姓名）。

## 原则

- **一个坑一个 case**：修过的每个识别 bug 都应留下一个 case，教训才不会随会话/人员流失。
- case 只增不删；文档本身作废时把 `note.md` 标注清楚再删，并在提交信息里说明。
- 语料库为空时测试会直接失败（`test_corpus_not_empty`），防止目录被误删后护栏静默消失。
